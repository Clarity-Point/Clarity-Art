параллельных запросах, удаление приватных файлов, границы организаций, уведомления

## Проверки

- Все миграции, включая атомарную `20261110180000_preserve_user_data`, применены к
  новой временной PostgreSQL 18.6. Схема сверена через `prisma migrate diff`.
- `npm run check`: ESLint, Prettier, TypeScript, тесты, production-сборки и gate
  зависимостей. Backend: 81 тест; frontend: 28; gate: 4.
- 26 Playwright-тестов: матрица 24 маршрутов × 3 ширины × 2 темы, axe,
  клавиатура и пользовательские сценарии, включая конфликты и уведомления.
- Интеграционные проверки используют HTTP и PostgreSQL; отказ диска моделируется,
  доставка писем проверяется локальным SMTP-сервером.
- В предыдущем GitHub CI прошли серверные проверки, сборки обоих Docker-образов
  и поиск секретов, но упали два сценария 320 px. Это уточняет локальные результаты
  предыдущего отчёта; исправление включено в текущий проход.

Повторный CI для `fcc5ce2` подтвердил серверные проверки и оба Docker-образа,
но обнаружил оставшееся переполнение. Оно воспроизведено локально со шрифтом
DejaVu Sans: минимальная ширина блока помощи растягивала основную сетку до 345 px.
Исправлены колонки сетки и мобильное расположение кнопки; ширина стала 320 px.
Стресс-тест теперь использует этот шрифт, а матрица печатает размеры и классы
выходящих за экран элементов для диагностики будущих сбоев. Дополнительный проход
всех маршрутов на 320 px с этим шрифтом выявил и исправил перенос переключателей
админ-панели; этот вариант шрифта включён в постоянную мобильную матрицу.

Локально: Node.js 26.8.1, npm 12.0.2, Chromium Playwright. CI использует Node.js 22
и PostgreSQL 16. Браузерные тесты работают с API-фикстурами; это не сквозной
production E2E. Обновление рабочего сервера в рамках аудита не выполнялось.

## Обновление и ограничения

Сначала примените миграцию, затем обновите backend и frontend вместе. Старый клиент
без `version` при редактировании дневника получает 400 и должен обновить страницу.
Индексы создаются обычным CREATE INDEX внутри транзакции: на большой рабочей БД
планируйте окно обновления и измерьте длительность на её копии.

Очередь удалений хранится в БД и обрабатывается при старте, после удаления аккаунта
и каждую минуту, до 50 файлов за проход. После исправления прав/диска повторение
автоматическое. Для нескольких backend-реплик нужен общий IMAGE_STORAGE_DIR;
независимые локальные каталоги с общей БД не поддерживаются. Диагностика описана
в [runbook](../operations/runbook.md).

## Оставшиеся работы по приоритету

1. Перед публичным запуском: staging-проверка HTTPS/cookie, reverse proxy,
   реальной доставки SMTP, согласия и внешнего AI; восстановление PostgreSQL
   вместе с рисунками из резервной копии. Эти среды здесь не проверялись.
2. До нескольких реплик: общий каталог рисунков, общий rate-limit store,
   бюджет и ограничение параллельных AI-операций. Локальный rate limit не общий.
3. Контент и права: архивирование курсов, передача роли организации и разрешение
   конфликтов нескольких модераторов. Сейчас удаление используемого курса
   блокируется, а передачи прав через интерфейс ещё нет.
4. Рост данных: пагинация кабинета специалиста и списка проверок администратора;
   EXPLAIN и нагрузочные измерения на репрезентативных объёмах. Переход от поиска
   подстроки к полнотекстовому поиску требует измерений.
5. Файлы: сверка сирот после аварии между записью файла и созданием ImageAnalysis.
   Новая очередь покрывает удаление аккаунта, но не устраняет это отдельное окно.
6. Зависимости: остаются предупреждения moderate/low; high/critical отсутствуют
   в локальном gate. Принудительные откаты пакетов не применялись.
7. Интерфейс: ручная проверка screen reader, Safari/Firefox, физических устройств
   и незавершённого редактирования при уходе со страницы. Автотесты не заменяют её.

Смена стека, новая система дизайна и дополнительные облачные сервисы не добавлялись.
Этот проход закрывает перечисленные дефекты, а не объявляет весь проект или
рабочую инфраструктуру проверенными без ограничений.
