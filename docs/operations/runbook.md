# Эксплуатация

## Локальная разработка

### Docker Compose

Скопируйте `.env.example` в `.env` в корне и задайте `JWT_SECRET` и
`POSTGRES_PASSWORD`. Запустите стек разработки и примените миграции.

```bash
docker compose -f docker-compose.dev.yml up -d --build
docker compose -f docker-compose.dev.yml exec backend npx prisma migrate deploy
```

Приложение открывается на [localhost:5173](http://localhost:5173), API работает на
порту 3100, Swagger доступен на [localhost:3100/api-docs](http://localhost:3100/api-docs).

### Запуск на хосте

Используйте свежий патч Node.js 22 и PostgreSQL 16. Базу также можно запустить
через `docker compose -f docker-compose.dev.yml up -d db`. Она по умолчанию
доступна с хоста на порту 5433.

```bash
npm ci --include=dev
cp backend/.env.example backend/.env
cp frontend/.env.example frontend/.env
```

Укажите `DATABASE_URL` и уникальный `JWT_SECRET` (минимум 32 байта).
Генерация секрета: `openssl rand -hex 32`. Не отправляйте секрет в журналы или Git.

```bash
npm run prisma:generate -w backend
(cd backend && npx prisma migrate deploy)
npm start
```

Демо-наполнение запускайте только в тестовой базе: `npm run prisma:seed -w backend`.
Адреса и пароль демо-аккаунтов заданы в [seed.js](../../backend/prisma/seed.js).
Для презентационного наполнения временной базы после seed запустите
`(cd backend && node prisma/enrich-demo.js)`. Скрипт пересоздаёт записи демо-аккаунтов
и сообщения демонстрационной организации.

В корне доступны `npm run dev -w frontend`, `npm run build -w frontend` и
`npm test -w frontend`. Vite проксирует `/api` на `http://localhost:3100`.
Адрес прокси меняется через `VITE_PROXY_TARGET`. В собранном приложении API
доступен по `/api` на том же origin. При раздельном размещении согласуйте CORS,
cookie и CSP.

## Настройка AI

Приложение поддерживает OpenAI-совместимый `/chat/completions`. Без настроенного
провайдера чат и анализ рисунков возвращают встроенные ответы.

Для backend, запущенного на хосте, пример настройки в `backend/.env` выглядит так.

```dotenv
AI_BASE_URL=http://localhost:11434/v1
AI_MODEL=llama3.1
AI_VISION_MODEL=llava
AI_DATA_PROCESSING_MODE=local
```

В Docker Compose задайте эти переменные в корневом `.env`. Адрес `AI_BASE_URL`
должен быть доступен из контейнера backend. Для провайдера в той же сети Compose
используйте имя его сервиса.

На Linux Compose разрешает `host.docker.internal` через мост Docker.
Если Ollama запущен на хосте, укажите
`AI_BASE_URL=http://host.docker.internal:11434/v1`. Ollama должен принимать
соединения на интерфейсе, доступном Docker. Ограничьте порт сетью Docker.
Провайдер в отдельном контейнере той же закрытой сети может работать без
публикации порта хоста. [Документация Docker](https://docs.docker.com/compose/how-tos/networking/#custom-dns-with-extra_hosts)

Для слабого хоста можно задать в окружении самого Ollama
`OLLAMA_NUM_PARALLEL=1` и `OLLAMA_MAX_LOADED_MODELS=1`. Это ограничивает
параллельную работу и объём памяти под модели. При разных моделях для
текста и изображений первый запрос после их смены может идти дольше.
Проверьте оба сценария на своей машине. Если CPU-провайдеру нужно больше
времени, Compose передаёт `AI_CHAT_TIMEOUT_MS` и `AI_IMAGE_TIMEOUT_MS`
в backend. В штатной конфигурации nginx ждёт ответ до 300 секунд, поэтому
для обычных запросов через Compose оставьте запас до этого предела.
`AI_SCREEN_TIMEOUT_MS` ограничивает время вспомогательной обработки
записи. [Настройки Ollama](https://docs.ollama.com/faq) ·
[Аппаратная совместимость и запуск на CPU](https://docs.ollama.com/gpu)

Указывайте `local` только для провайдера на собственной инфраструктуре.
Для внешнего сервиса задайте `external` и при необходимости `AI_API_KEY`.
Внешняя обработка требует явного согласия, которое пользователь может отозвать
в профиле. Встроенная конфигурация OpenRouter всегда использует внешний режим.

## Проверки перед изменением окружения

```bash
npm run check
npx playwright install chromium
npm run test:browser
```

Если Chromium установлен системой:

```bash
PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium npm run test:browser
```

Браузерные тесты используют фикстуры API, проверяют интерфейс и не подтверждают
интеграцию с реальной базой или AI. Для интеграционного прохода нужны отдельная
тестовая база и пользователи всех ролей. CI дополнительно применяет миграции к
чистой PostgreSQL и сравнивает схему, собирает Docker-образы.

Для локального аналога стадии CI используйте временную базу с применёнными
миграциями. Проверка зависимостей всегда включает дерево инструментов разработки.

```bash
RUN_DATABASE_TESTS=true DATABASE_URL='postgresql://user:password@localhost:5432/clarity_test' npm run check
```

Проверки SMTP запускают локальный тестовый сервер. Результаты и ограничения
описаны в [аудите](../audits/2026-11-23.md).

## Публикация и запуск

Workflow публикации образов зависит от полного CI. Он формирует SBOM и provenance.
Staging публикуется после успешного CI для push в main. Публикация образа сама
по себе не является проверкой доступности развёрнутого сервиса.

Compose использует образы `ghcr.io/clarity-point/clarity-art-backend` и
`ghcr.io/clarity-point/clarity-art-frontend`. Для установки определённого
релиза задайте `BACKEND_IMAGE` и `FRONTEND_IMAGE` в `.env`.

В production задайте `NODE_ENV=production`, точный `FRONTEND_URL` с протоколом и
портом, сильные пароли БД, HTTPS и `COOKIE_SECURE=true`. `FRONTEND_URL` задаёт также
разрешённый Origin изменяющих API-запросов. Не используйте `*`.
Доверие `TRUST_PROXY` ограничьте адресами действительного reverse proxy.
Не открывайте PostgreSQL и backend напрямую в интернет.

```bash
docker compose config --quiet
docker compose pull
docker compose up -d
```

`/health` — жив ли процесс; `/health/ready` — доступна ли БД. Проверяйте readiness
при обновлении. Backend пишет структурированные журналы с идентификатором запроса;
дневники, изображения, пароли и тексты чатов туда попадать не должны.

## Резервные копии и восстановление

Сохраняйте вместе дамп PostgreSQL и том `image_data`. До миграции делайте резервную
копию и фиксируйте digest текущих образов. Сам дамп БД не восстанавливает рисунки.
Храните копии вне сервера, шифруйте, ограничивайте доступ и проверяйте срок хранения.

Проводите пробное восстановление в изолированное окружение: восстановите БД и
рисунки, примените миграции, проверьте readiness, вход, дневник и выдачу изображения.
Проверяйте, что чужие изображения и записи недоступны. Не запускайте AI-запросы на
боевых данных в тестовом окружении без соответствующих условий обработки.

Откат приложения на старый образ безопасен только при совместимости схемы.
Восстановление БД из копии теряет записи после времени копирования; согласуйте
этот момент до восстановления.

Скрипты резервного копирования и восстановления используют Bash, Docker Compose,
GPG, OpenSSL и Python 3.11 или новее. Выполняйте команды из каталога исходного
Compose-проекта. В хранилище GPG должен быть открытый ключ получателя, а у
ответственного за восстановление закрытый ключ. Для команды используется полный
отпечаток. Выберите каталог, доступный только оператору, и сохраните зашифрованный
комплект вне сервера.

```sh
docker compose -p clarity-art stop backend
/path/to/Clarity-Art/scripts/clarity-backup.sh clarity-art /private/backup/clarity.tar.gpg GPG_FINGERPRINT
docker compose -p clarity-art start backend
```

Перед копированием остановите внешние процессы, которые могут писать в базу
или том рисунков, и оставьте PostgreSQL запущенной. Служба frontend может
работать в течение окна обслуживания. Команда проверяет остановку backend
до и после копирования, собирает совместимый набор и шифрует его до публикации
в указанном каталоге.

```sh
/path/to/Clarity-Art/scripts/clarity-restore-test.sh /private/backup/clarity.tar.gpg BACKEND_IMAGE
```

Команда создаёт отдельную БД и том рисунков в новой закрытой Docker-сети.
Второй аргумент необязателен. Чтобы проверить приложение, передайте образ
backend этой версии, уже доступный на хосте. Скрипт запускает его с новым
ключом сессий, выключенными ИИ и SMTP и проверяет готовность. Рабочий Compose
в качестве цели не используется. После учения остановите и удалите тестовые
контейнеры, сеть и оба тома по именам из вывода. Для незашифрованных временных
файлов используйте `TMPDIR` на защищённом носителе. Команда
`tests/tooling/backup-smoke.sh BACKEND_IMAGE` проверяет синтетическую копию и
доступы через API.

## Порядок обновления обратной связи и внешнего ИИ

На время смешанного выпуска установите `PRACTICE_FEEDBACK_NOTIFICATIONS=false`.
После обновления всех backend-реплик включите запись системных уведомлений.
Для отката сначала остановите запись этих типов на всех репликах и дождитесь
завершения транзакций. Удалите только уведомления типов `practice_share` и
`practice_recommendation` со ссылкой на подборку, затем запускайте прежний backend.

Для внешней обработки задайте `AI_PROVIDER_LABEL` и уникальный
`AI_PROVIDER_POLICY_REVISION` для текущего поставщика, моделей и условий обработки.
При смене обработчика, включая возврат к прежнему, задайте новую версию.
Существующее согласие с датой и без идентификатора не разрешает внешнюю передачу.
Для первого пилота оставьте внешнюю обработку выключенной. Удалите
`AI_BASE_URL`, `AI_API_KEY` и `OPENROUTER_API_KEY` из окружения всех реплик
и дождитесь завершения активных вызовов перед миграцией или откатом.
При откате на старый backend сохраняйте внешнюю обработку выключенной.
Перед её повторным включением назначьте новую версию политики.

## При росте нагрузки

Rate limiter хранит счётчики в памяти процесса. Для нескольких реплик нужен общий
store, например Redis, и проверка доверия к proxy. Настройте мониторинг 5xx, задержки,
readiness, свободного диска и ошибок AI. Целевые SLO, RPO и RTO определяются перед
пилотом и подтверждаются измерениями.

## Диагностика запросов и аудит

`LOG_FORMAT=json` выдаёт структурированные события; `LOG_LEVEL` фильтрует
операционные сообщения. `requestId` из `X-Request-Id` связывает HTTP, сервисы и
аудит в рамках запроса. В access log записывается шаблон маршрута, а неизвестный
путь обозначается `[unmatched]`. Nginx пишет метод, статус, длительность и ID
ответа backend, без строки запроса и Referer.

Ошибки сериализуются как тип, безопасный код и числовой статус. Текст и стек могут
содержать данные Prisma/AI и не сохраняются. Клиентская console также не получает
объекты запросов. Для расследования используйте название операции, код и requestId.
Не включайте запись тел запросов в reverse proxy или внешнем сборщике.

События `module=audit` пишутся на уровне info независимо от поднятого `LOG_LEVEL`.
Значение `silent` отключает и аудит. Перенаправляйте аудит в хранилище с ограниченным
доступом и согласованным сроком хранения: сам stdout не обеспечивает неизменяемость.
Успешные health-пробы пропускаются, ошибки readiness и обрывы клиента записываются;
у последних `aborted=true`, HTTP-статус может отражать уже отправленные заголовки.

## Повторное удаление рисунков

Удаление аккаунта помещает ключи рисунков в `ImageDeletion` в той же транзакции,
которая удаляет пользователя. Событие `account.deleted` содержит `imagesQueued`:
это количество поставленных задач, а не подтверждение физического удаления.

Обработчик запускается при старте backend, после удаления аккаунта и каждую минуту.
За проход выбирается до 50 готовых задач. Отсутствующий файл считается уже удалённым;
ошибки доступа и диска оставляют задачу для повторения через минуту. Задачи переживают
перезапуск процесса. Проверка очереди без чтения пользовательских данных:

```sql
SELECT count(*) AS pending,
       count(*) FILTER (WHERE "nextAttemptAt" <= now()) AS due
FROM "ImageDeletion";
```

При росте очереди проверьте события `module=imageDeletion`, безопасный `err.code`,
права пользователя backend и доступность `IMAGE_STORAGE_DIR`. После исправления
причины задачи выполнятся автоматически. Не очищайте очередь вручную до удаления
соответствующих файлов. В логах есть ключ файла, но нет содержимого изображения.

Все backend-реплики должны видеть один каталог рисунков. Общая БД с независимыми
локальными каталогами не поддерживается: отсутствие файла на одной реплике не
означало бы его отсутствие на другой. Резервная копия БД должна включать очередь;
при восстановлении сохраняйте её вместе с согласованной копией каталога рисунков.
Срок удаления данных из резервных копий задаётся отдельной политикой хранения.

Очередь не сканирует файлы, оставшиеся после аварии в момент создания анализа.
Сверку таких сирот следует сначала выполнять в режиме отчёта; автоматическое
удаление по одному лишь возрасту файла может затронуть незавершённые запросы.
