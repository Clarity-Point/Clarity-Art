# Эксплуатация

## Локальная разработка

Используйте Node.js 22.12+ и PostgreSQL 16 либо Docker Compose.

```bash
npm ci
cp backend/.env.example backend/.env
cp frontend/.env.example frontend/.env
```

Укажите `DATABASE_URL` и уникальный `JWT_SECRET` (минимум 32 байта).
Генерация секрета: `openssl rand -hex 32`. Не отправляйте секрет в журналы или Git.

```bash
npm run prisma:generate -w backend
(cd backend && npx prisma migrate deploy)
npm start
```

Демо-наполнение запускайте только в тестовой базе: `npm run prisma:seed -w backend`.
Учётные записи из seed имеют известные пароли; не наполняйте ими публичную установку.

## Проверки перед изменением окружения

```bash
npm run check
npx playwright install chromium
npm run test:browser
```

Если Chromium установлен системой:

```bash
PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium npm run test:browser
```

Браузерные тесты используют фикстуры API, проверяют интерфейс и не подтверждают
интеграцию с реальной базой или AI. Для интеграционного прохода нужны отдельная
тестовая база и пользователи всех ролей. CI дополнительно применяет миграции к
чистой PostgreSQL и сравнивает схему, собирает Docker-образы.

## Публикация и запуск

Workflow публикации образов зависит от полного CI. Он формирует SBOM и provenance.
Staging публикуется после успешного CI для push в main. Публикация образа сама
по себе не является проверкой доступности развёрнутого сервиса.

В production задайте `NODE_ENV=production`, точный `FRONTEND_URL` с протоколом и
портом, сильные пароли БД, HTTPS и `COOKIE_SECURE=true`. `FRONTEND_URL` задаёт также
разрешённый Origin изменяющих API-запросов. Не используйте `*`.
Доверие `TRUST_PROXY` ограничьте адресами действительного reverse proxy.
Не открывайте PostgreSQL и backend напрямую в интернет.

```bash
docker compose config --quiet
docker compose pull
docker compose up -d
```

`/health` — жив ли процесс; `/health/ready` — доступна ли БД. Проверяйте readiness
при обновлении. Backend пишет структурированные журналы с идентификатором запроса;
дневники, изображения, пароли и тексты чатов туда попадать не должны.

## Резервные копии и восстановление

Сохраняйте вместе дамп PostgreSQL и том `image_data`. До миграции делайте резервную
копию и фиксируйте digest текущих образов. Сам дамп БД не восстанавливает рисунки.
Храните копии вне сервера, шифруйте, ограничивайте доступ и проверяйте срок хранения.

Проводите пробное восстановление в изолированное окружение: восстановите БД и
рисунки, примените миграции, проверьте readiness, вход, дневник и выдачу изображения.
Проверяйте, что чужие изображения и записи недоступны. Не запускайте AI-запросы на
боевых данных в тестовом окружении без соответствующих условий обработки.

Откат приложения на старый образ безопасен только при совместимости схемы.
Восстановление БД из копии теряет записи после времени копирования; согласуйте
этот момент до восстановления. Автоматизированного backup/restore в проекте пока нет.

## При росте нагрузки

Rate limiter хранит счётчики в памяти процесса. Для нескольких реплик нужен общий
store, например Redis, и проверка доверия к proxy. Настройте мониторинг 5xx, задержки,
readiness, свободного диска и ошибок AI. Целевые SLO, RPO и RTO определяются перед
пилотом и подтверждаются измерениями.

## Диагностика запросов и аудит

`LOG_FORMAT=json` выдаёт структурированные события; `LOG_LEVEL` фильтрует
операционные сообщения. `requestId` из `X-Request-Id` связывает HTTP, сервисы и
аудит в рамках запроса. В access log записывается шаблон маршрута, а неизвестный
путь обозначается `[unmatched]`. Nginx пишет метод, статус, длительность и ID
ответа backend, без строки запроса и Referer.

Ошибки сериализуются как тип, безопасный код и числовой статус. Текст и стек могут
содержать данные Prisma/AI и не сохраняются. Клиентская console также не получает
объекты запросов. Для расследования используйте название операции, код и requestId.
Не включайте запись тел запросов в reverse proxy или внешнем сборщике.

События `module=audit` пишутся на уровне info независимо от поднятого `LOG_LEVEL`.
Значение `silent` отключает и аудит. Перенаправляйте аудит в хранилище с ограниченным
доступом и согласованным сроком хранения: сам stdout не обеспечивает неизменяемость.
Успешные health-пробы пропускаются, ошибки readiness и обрывы клиента записываются;
у последних `aborted=true`, HTTP-статус может отражать уже отправленные заголовки.

Полный проход с БД выполняется только на отдельной тестовой базе:

```bash
RUN_DATABASE_TESTS=true DATABASE_URL='postgresql://user:password@localhost:5432/clarity_test' npm run check
```

Перед ним примените миграции. Проверки SMTP используют локальный тестовый сервер
и не отправляют реальные письма. Сведения о текущем покрытии и ограничениях:
[аудит 10 ноября](../audits/2026-11-10.md).
