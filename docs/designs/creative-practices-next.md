# Следующий этап творческих практик Clarity-Art

Первый выпуск даёт новичку попробовать «Две линии» по ссылке и скачать рисунок.
Участник с аккаунтом может вернуться к сохранённому черновику. Затем добавляются
подбор практик по намерению и обратная связь специалиста. До пилота с реальными
данными проверяется восстановление приложения. Внешний ИИ допускается в пилот
после привязки согласия к конфигурации обработки.

## 1. Первая практика без регистрации

На странице «Две линии» из печатной подборки и на экране входа появляется ссылка
«Попробовать на холсте». Она открывает публичный `/practice-demo`. Экран берёт
карточку `two-lines` из существующего публичного `GET /api/practices/catalog`.
На нём доступны инструкция, холст и скачивание PNG. Печатная карточка сохраняет
свой адрес и разметку.

Вынести инструменты холста из `PracticeSession` в общий компонент, сохранив
`useCanvasDrawing` и обычные точки входа. Гостевой экран хранит состояние рисунка
в памяти компонента и рисует PNG в браузере. Он обращается только к публичному
каталогу. При переходе к входу с несохранённым рисунком предложить сначала скачать
PNG. После входа пользователь загружает этот файл в альбом через существующую
форму. Такой переход работает после перезагрузки и на другом устройстве, если
файл у человека под рукой. Перенос через хранилище браузера потребовал бы
отдельного управления личными файлами на общем устройстве.

**Приёмка.** В чистом контексте браузера открыть ссылку, нарисовать линию мышью
и касанием и скачать PNG с нарисованным штрихом. Проверить пиксели в области
штриха. Перехват запросов подтверждает отсутствие
вызовов профиля, альбома и ИИ и отправки байтов рисунка. Проверить предупреждение
при уходе, вход по ссылке из демо, загрузку PNG в альбом и печать карточки на A4.
Если каталог временно недоступен, показать ошибку с кнопкой повторной загрузки.

## 2. Продолжение незаконченной работы

На практике с аккаунтом загружается черновик текущего упражнения. Пользователь
видит «Сохраняем…», «Черновик сохранён» или ошибку с повтором. На главной и в
каталоге ссылка «Продолжить практику» открывает последний непустой черновик.
По каждой карточке хранится одна версия в работе. Завершение упражнения и
сохранение в альбом остаются отдельными действиями. Завершённое упражнение
можно продолжить, пока в нём есть черновик.

| Контракт                                          | Поведение                                                                                                                             |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/practices/drafts`                       | Только ID карточек с непустыми черновиками и время изменения. Порядок по времени изменения с устойчивым разрешением совпадений по ID. |
| `GET /api/practices/drafts/:practiceId`           | Данные черновика, `version` и UUID последней записи. Для новой ячейки версия 0 и пустые данные.                                       |
| `PUT /api/practices/drafts/:practiceId`           | Полный снимок, ожидаемая `version` и UUID записи. Ответ содержит принятую версию. Явная очистка отправляет пустой снимок.             |
| `POST /api/practices/drafts/:practiceId/finalize` | Ожидаемая версия и идемпотентный UUID запроса. API создаёт работу из серверного снимка и очищает черновик в одной транзакции.         |

Черновик хранится в PostgreSQL с ключом `(userId, practiceId)`, версией,
UUID последней записи, датой, названием, подписью, выбранным режимом и одним вложением с признаком
«холст» или «фото». Как и альбом, черновик принимает PNG, JPEG или WebP до
1 МиБ. API принимает один объект `image` с MIME и base64, как при создании
работы. Режим можно переключать без удаления вложения. При замене рисунка
фотографией или наоборот запросить подтверждение. Продолжать рисовать на
сохранённом холсте можно сразу после загрузки. Перед сохранением в альбом
показать фактическое вложение. Смена режима сама по себе оставляет пустой
черновик пустым.

Переиспользовать проверку ожидаемого аккаунта из API практик, учёт версий
и задержку записи текста из дневника. Хранить байты отдельной колонкой
и выдавать черновик только владельцу с `no-store`. При записи блокировать
строку владельца тем же способом, что при сохранении работ, сверять версию
и увеличивать её. После очистки остаётся пустая ячейка с новой версией,
поэтому отложенный запрос не восстановит старый черновик. Ключ финализации
использует существующий механизм идемпотентности работ и проверяется до
чтения черновика. Отметка об удалённой работе по ключу владельца всегда
даёт HTTP 410. В существующей работе сравниваются ID упражнения и версия
исходного черновика. Повтор для той же версии возвращает созданную
работу, а ключ другой операции даёт HTTP 409. При лимите альбома, пустой подписи без рисунка
или устаревшей версии черновик сохраняется, создание отклоняется.
При `409 DRAFT_CONFLICT` перечитать серверный снимок. После потери ответа
PUT подтверждением служат совпадение UUID записи и версия ровно на единицу
выше ожидаемой. Очередь новых изменений при этом сохраняется. При
расхождении оставить локальный вариант и дать скопировать текст или
скачать рисунок перед заменой серверным вариантом.

Редактор становится доступен после чтения черновика и загрузки его PNG
на редактируемый холст. При ошибке чтения показать повтор. Пакетировать
штрихи и ввод текста. Первый снимок отправляется после короткой паузы,
дальнейшие автоотправки идут с интервалом от 20 секунд. Одна запись активна
за раз. Ответ подтверждает только отправленный снимок, а более свежие
изменения остаются в очереди.

Для точного маршрута `PUT /api/practices/drafts/:practiceId` нужен отдельный
бюджет для часто обновляемых снимков. Начальные лимиты для одной реплики —
300 PUT на IP и 60 на аккаунт за 15 минут. IP проверяется до чтения тела,
аккаунт после аутентификации. Этот маршрут использует свой лимит тела,
достаточный для одного изображения в base64, и отдельные бюджеты вместо
общего лимита 100 запросов на IP за 15 минут. Остальные маршруты работают
с текущим общим ограничением. При HTTP 429 сохранять ожидающий снимок
и показать время до повторной попытки по `Retry-After`. Перед настройкой
нескольких реплик использовать предусмотренный в инструкции общий
счётчик лимитов.

Перед «Сохранить в альбом» временно приостановить редактирование, подтвердить
текущий снимок и зафиксировать его версию и UUID финализации. При потере
ответа повторять тот же UUID и версию до получения результата. После
подтверждения перечитать черновик, чтобы увидеть новую версию очистки или
изменения другой вкладки. При смене аккаунта очистить локальную работу
и отменить ожидающие запросы. Черновик входит в экспорт владельца и
каскадно удаляется с аккаунтом. Подборки используют сохранённые работы
из альбома.

**Приёмка.** После статуса «Черновик сохранён» закрыть вкладку, войти с другого
устройства и увидеть подтверждённый рисунок и подпись. При закрытии до
подтверждения возможна потеря последних штрихов. Для этого состояния показать
предупреждение браузера, пока оно доступно, и предложить скачать рисунок.
Проверить первый штрих после восстановления, две вкладки, поздний ответ
во время нового штриха, смену аккаунта, потерю ответа PUT и финализации,
возврат к тому же содержимому после записей другой вкладки,
создание нового черновика после неё, очистку, запись после очистки,
достижение лимита альбома и экспорт. PostgreSQL-тест проверяет, что
параллельная финализация создаёт одну работу. Проверить HTTP 410 при
повторе ключа удалённой работы, в том числе с другим упражнением.
Прогон с production-лимитами
проверяет продолжительную практику, несколько аккаунтов с общим IP,
HTTP 429 и доступ к остальным разделам при исчерпании бюджета автосохранения.

## 3. Уведомление и обратная связь от специалиста

В первой версии после выдачи доступа специалист получает одно уведомление
«Новая подборка к встрече». Открытие ведёт в его кабинет. В самой подборке
есть кнопка «Отметить как просмотренную». Автор видит «Специалист отметил
как просмотренную» в исходящих. Автоматический статус чтения не нужен.

- В транзакции выдачи доступа создавать строку `Notification` с
  `practiceShareId` и общим текстом без имени, названия работ и подписей.
  Уникальность `(userId, practiceShareId, type)` исключает дубликаты. Для
  прежних типов связь остаётся пустой. Адрес действия формируется приложением
  из известного типа и ведёт в «Подборки к встрече».
- `PUT /api/therapist/practice-shares/:id/acknowledgement` идемпотентно
  ставит `acknowledgedAt`. Выборка и запись требуют текущую роль
  `THERAPIST`, точного получателя, действующую подборку и хотя бы одну
  оставшуюся работу. Просмотренный статус входит в списки владельца и
  выбранного специалиста. Несовпадение сессии даёт HTTP 409, неверная роль
  HTTP 403, недоступная подборка HTTP 404.
- При отзыве очищать отметку и связанные уведомления в той же транзакции.
  При удалении последней работы очищать отметку и уведомления в той же
  транзакции удаления. Удаление аккаунта убирает связанные строки каскадно.
  Список уведомлений и его счётчик для событий о подборке используют
  одинаковый фильтр текущего доступа. Этот же фильтр используют отметка
  прочтения уведомления и JSON-экспорт. Если курсор указывает на удалённое
  или недоступное событие, вернуть `409 NOTIFICATIONS_CHANGED`, а клиент
  заново загружает первую страницу. При возврате фокуса обновлять
  уведомления открытой панели.

Во второй версии автор при создании подборки может явно включить
«Разрешить предложить практику». Значение по умолчанию выключено. Специалист
может отправить один ID из существующего каталога на подборку. Для
`PUT /api/therapist/practice-shares/:id/recommendation` действуют те же
проверки роли и доступа, плюс повторная проверка разрешения автора в
транзакции. Повтор того же ID возвращает сохранённую рекомендацию, попытка
выбрать другой ID после отправки получает HTTP 409. Владелец может
выключить разрешение через `PUT /api/practices/shares/:id/recommendation-permission`
с `allowed: false`. Чтобы снова разрешить рекомендацию, он создаёт
новую подборку. Владелец видит «Открыть практику» в альбоме и может скрыть
совет через `PUT /api/practices/shares/:id/recommendation/dismissal`.
Скрытие убирает совет и уведомление у владельца, сохраняя результат
первой отправки для повторов. Отзыв доступа или выключение разрешения
удаляет рекомендацию из выдачи, убирает уведомление и блокирует повтор
отправки. Обе операции владельца идемпотентны.
Если участник уже начал упражнение, его собственный черновик и прогресс
сохраняются. Переписка и произвольные тексты специалиста остаются за
пределами этого выпуска.

Операции получателя сериализуются с отзывом по строке той же подборки.
Операции удаления работы проверяют доступность её подборок до подтверждения
транзакции. Все сервисы придерживаются порядка блокировок владелец →
подборка → дочерние строки. Это сохраняет предсказуемый порядок между
повторной отправкой, отметкой, отзывом и удалением последней работы.

Уведомления создаются для новых подборок. Включать запись новых типов
после обновления всех реплик, читающих уведомления. Перед откатом
выключить запись этих типов на всех репликах и дождаться завершения
активных транзакций. Затем удалить системные уведомления по выделенным
типам и запустить старый backend. Сами подборки и их содержимое сохраняются.

**Приёмка.** Два повтора выдачи создают одно уведомление. Только выбранный
специалист ставит отметку, а повтор сохраняет её время. Подборка, отметка и
уведомление исчезают после отзыва и после удаления последней работы. Проверить
демоцию специалиста, недоступную отметку о прочтении, экспорт, удалённый
курсор, удаление обоих аккаунтов и параллельный отзыв. Отдельно
проверить, что рекомендация требует явного разрешения, отклоняет неизвестный
ID, исчезает после скрытия или выключения разрешения и не появляется заново
при повторе запроса. Проверить, что на этапе отката новые события не
создаются между очисткой и запуском прежнего backend.

## 4. Выбор практики по намерению

К существующим фильтрам времени и материалов добавить выбор намерения.
В первом выпуске достаточно трёх вариантов с привязкой к уже выпущенным
карточкам.

| Как показываем          | Карточки                            |
| ----------------------- | ----------------------------------- |
| Порисовать без темы     | «Две линии», «Три формы»            |
| Заметить деталь дня     | «Кадр из дня», «Маленькая открытка» |
| Подготовиться к встрече | «Маленькая открытка», «Три формы»   |

В `GET /api/practices/catalog` добавить опциональный список намерений с
устойчивыми ID и ID карточек. Маршрут `/practices?intent=…` отражает
текущий выбор для ссылки и кнопки «Назад». Неизвестное значение ведёт к
общему списку. Ссылки из результатов передают выбранное намерение на экран
упражнения. «Все практики» возвращает его в каталог. При сочетании фильтров
применяется их пересечение. Пустой
результат предлагает сбросить фильтры. Намерение не запрашивает анкету,
не интерпретирует дневник и не передаётся ИИ. Существующие ссылки, серии,
прогресс и печатная раскладка сохраняют свои ID.

**Приёмка.** Участник находит карточку по намерению, уточняет результат
длительностью и возвращается с сохранённым намерением через «Назад» и
«Все практики». Проверить
неизвестное намерение, отсутствие нового поля на старом backend, пустую
выдачу и управление с клавиатуры. Статический тест проверяет уникальность
ID и присутствие всех карточек намерений в каталоге.

## 5. Готовность к пилоту

Первый пилот с реальными данными проводится с добровольными
совершеннолетними участниками после письменного одобрения по дорожной
карте. Условия включают выключенный внешний ИИ, назначенного человека
для обращений и журнал инцидентов без содержимого работ. Включение
внешнего ИИ потребует отдельного решения оператора пилота после
проверки механизма согласия. Для выключения убрать `AI_BASE_URL`,
`AI_API_KEY` и `OPENROUTER_API_KEY` из окружения всех экземпляров
backend. Значение режима `local` само по себе оставляет обработку
включённой при заданном локальном endpoint.

### Восстановление базы и рисунков

Подготовить две штатные команды оператора для резервного копирования и
тестового восстановления. Копия содержит дамп PostgreSQL, том
`image_data` и манифест с версией схемы, digest образов, временем
создания и контрольными суммами файлов. Альбом и черновики входят в дамп.
Старые изображения анализа хранятся в отдельном томе. На время получения
совместимой пары требуется короткое окно обслуживания с остановкой
всех записывающих backend-процессов и фоновой чистки файлов. Публиковать
завершённый комплект в резервное хранилище после проверки обеих частей.
Хранить комплект зашифрованным вне сервера. Ключи и доступ к нему
задаёт оператор установки.

Восстанавливать в новый изолированный Docker-контур с автоматически выбранным именем, новой БД и томами.
Перед записью проверять контрольные суммы и наличие обеих частей. Команда
проверяет, что выбранный проект, адрес БД и имена подключённых томов
отличаются от рабочих и цель пуста. Для автоматической проверки в CI использовать
синтетические записи дневника, альбома и старого рисунка. Проверять вход,
readiness, выдачу файлов владельцу, отказ второму аккаунту и состояние
отозванной подборки. Отдельно проверить отказ при повреждённой копии,
непустой цели и выборе рабочего контура. В реальном учении измерять время восстановления и
дату последней восстановленной записи. Допустимые потери и время простоя
согласует оператор пилота до подключения участников. Изолированный
контур восстановления запускается с отдельным ключом сессий и сетевой
изоляцией от ИИ, SMTP и рабочей инфраструктуры.

### Согласие на внешнюю обработку

Текущий механизм хранит время согласия в `Profile.aiDataConsentAt`.
Добавить ID политики согласия. Backend вычисляет непрозрачный ID из
нормализованного адреса провайдера, моделей текста и изображений и версии
политики оператора. Замена ключа доступа сама по себе не меняет ID.
Оператор задаёт новую версию политики при каждой смене обработчика или
условий, в том числе при возврате к прежнему провайдеру. Это касается
и изменения маршрутизации за тем же шлюзом. API показывает участнику отображаемое имя поставщика
и ID политики без адресов внутренних сервисов и ключей.

`GET /api/ai/status` добавляет поля политики. Существующее поле
`consentGiven` означает согласие именно для текущей внешней конфигурации.
`PUT /api/profile/ai-consent` требует `X-Expected-User-Id` для обеих операций.
Выдача также требует `policyId`, показанный пользователю. Устаревший ID
возвращает HTTP 409 с предложением перечитать настройки. Отзыв действует
для текущего аккаунта и очищает дату и ID независимо от показанной политики.
Старому клиенту нужно обновить страницу перед изменением согласия.
`canUseConfiguredAI` сверяет оба поля перед обращением к провайдеру.
Внешние HTTP-вызовы отклоняют перенаправления. Это относится и к
потоковым запросам, и к запросам классификации.
Для существующих дат без ID новая внешняя обработка требует повторного
решения участника. Сами записи дневника, рисунки и чаты сохраняются.

Миграция добавляет nullable-поле. Перед сменой политики остановить
внешние вызовы и дождаться завершения активных потоков. Обновить все
backend-реплики и клиент, затем включить внешнюю конфигурацию. При
откате на backend, который проверяет только дату, оставить внешние
вызовы выключенными. При следующем включении назначить новую версию
политики, чтобы дата, которую мог изменить старый backend, не образовала
действующую пару с прежним ID.

**Приёмка.** Тестовый провайдер видит ноль запросов после смены политики
до повторного согласия для чата, потокового чата, рисунка, обработки
дневника и анализа профиля. Проверить возврат к прежнему поставщику с
новой версией, выдачу и отзыв из устаревшей вкладки, смену пользователя
перед обеими операциями, старую запись согласия во время отката,
повторное обновление и перенаправление к другому получателю. После
явного разрешения текущей политики проверить успешный вызов. Отдельно
проверить режимы без внешней
обработки. Артефакт пробного восстановления содержит результат
сверки файлов и доступов без личных данных.

## Порядок выпуска

1. Гостевые «Две линии» и серверный черновик. Точки входа и тексты
   проверяются с новичками на тестовых аккаунтах. Два наблюдаемых
   сценария — человек скачал первый рисунок по ссылке и продолжил
   ранее сохранённую работу после закрытия вкладки.
2. Намерения в каталоге, уведомление и явная отметка просмотра.
   Следующим небольшим выпуском добавить добровольную рекомендацию.
3. Параллельно подготовить проверяемое восстановление и применить его
   до пилота с реальными данными. Привязку согласия закончить до включения
   внешнего ИИ после отдельного решения о его использовании.

Изменения схемы выпускать отдельными добавочными миграциями. Старый
клиент продолжит работать с привычными ответами каталога, альбома
и списка уведомлений. Откат экрана или маршрута оставляет новые таблицы
и данные до следующего выпуска. Для политики обработки действует отдельный
порядок отката из раздела выше. После каждой поставки прогнать
`npm run check` с изолированной PostgreSQL и затронутые браузерные
сценарии. Для пилота принимать обратную связь по завершению действий
без записи содержания рисунков и дневников в продуктовую аналитику.
